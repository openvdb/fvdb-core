fVDB sparse conv vs FlexGEMM

Re-run of FlexGEMM's README training benchmark against fVDB 0.7.0, with a profile of where fVDB spends its time and a proposal for a faster backend. October 2026.

  • FlexGEMM still wins in fp16 and tf32, by 2–9×. The README's fVDB bars are out of date in both directions, and in fp32 at mid resolution fVDB now ties or wins.
  • fVDB's default backend spends ~74% of GPU time in gather and scatter kernels. Its per-tap GEMMs alone take about as long as FlexGEMM's whole step.
  • Patching gather-scatter can at best reach parity. To win, fVDB needs an output-stationary masked implicit GEMM, added as a new ConvolutionPlan backend with a neighbor map built from NanoVDB leaves.
  • That backend keeps a bit more topology memory on thin shells (≈112N vs 8P bytes) but uses less peak memory, because it drops the per-tap scratch buffers. On dense volumes it keeps about half the topology memory.

Setup

The benchmark is FlexGEMM's tests/submconv/train_benchmark.py ported to fVDB's ConvolutionPlan API. Each iteration builds the grid and plan (or FlexGEMM's neighbor cache), runs L submanifold 3×3×3 layers forward, then runs backward. Inputs are one-voxel-thick sphere shells averaging 12.7 neighbors per voxel. Results are averaged over 20 iterations after 2 warmup iterations.

All times are in milliseconds. FlexGEMM's fp16 forward reaches about 276 TFLOP/s at 256,256 and an effective 2.3 TB/s at 1024,64. That figure exceeds DRAM bandwidth, so L2 is serving most of the reused rows.

1 · Gather and scatter dominate

The default backend loops over the 27 taps. For each tap it gathers rows into a buffer, runs a cuBLAS GEMM, and scatter-adds with per-element atomics. At 256,256 the 81 gather launches and 54 scatter launches take 16.3 of 22.0 ms. At 1024,64 they take 70.6 of 98.0 ms. These kernels move one scalar per thread, use 64-bit div/mod indexing, and use scalar fp16 atomics.

2 · The GEMMs alone match FlexGEMM

At 256,256 fVDB's GEMMs add up to about 5.2 ms, and FlexGEMM's whole forward plus backward takes 4.9 ms. Each per-tap GEMM round-trips its buffer through DRAM. At C=64 the GEMMs are thin and memory-bound.

3 · Small grids are launch-bound

Each layer launches about 216 kernels, and each GEMM runs for about 5 µs. The module stores weights as (K2,K1,K0,Ci,Co), but gs_conv permutes them to (K0,K1,K2,Ci,Co), which forces a .contiguous() copy three times per layer. At RES=16 these copies take 39% of GPU time.

4 · Plan build is 5–18× slower

The plan builds in two passes with atomic counters and probes the tree 27 times per voxel in each pass. This matters in pipelines where the grid changes every step. With a fixed grid the plan is built once.

5 · pred_gather_igemm computes dense leaves

It launches one CTA per 8³ leaf and computes every slot in the leaf. A thin shell fills only a few percent of each leaf, and at RES=8 the whole grid is a single CTA. It is TF32-only, and its backward pass falls back to gather-scatter.

What FlexGEMM does instead

It runs one fused kernel per pass, and each output row accumulates all of its taps in registers, so forward and input-gradient need no atomics. Rows are sorted by a Gray code of their neighbor mask, so each tile skips the taps none of its rows use. It uses split-K when N is small and autotunes its tiles in Triton.

Proposal: a masked implicit GEMM backend

ConvolutionPlan is the right home for this backend. It builds topology once, caches it, shares it across layers, and selects a backend through expert_config. A new "masked_igemm" backend would sit beside _GatherScatterBackend. But what the plan builds today is the wrong shape, and it doesn't keep leaf order.

Leaf-cooperative build

Each CTA calls probeLeaf once on the neighbor leaves of the leaves it covers and stages their bitmasks and offsets in shared memory. Each voxel then resolves its 27 taps with bitmask tests and popcounts instead of 27 tree walks. Rows come out in leaf order because voxel_idx already follows NanoVDB order. The next section covers scheduling CTAs over VBM blocks so sparse leaves don't leave threads idle. This should beat FlexGEMM's hash-based 4 ms build at RES=1024.

Tile ordering

Gray-code sorting groups rows that share a mask, but it breaks spatial locality. The sort only builds a permutation (sorted_idx), and feature data stays in leaf order. Three options to benchmark:

  • global Gray sort (FlexGEMM)
  • Gray sort within each leaf
  • no sort, plain leaf order

Where fVDB can pull ahead of FlexGEMM

  • Blackwell-native kernels. A CuTe kernel can use tcgen05, TMA gather, and warp specialization. FlexGEMM's Triton kernel reaches roughly half of dense fp16 peak at its best config, so the headroom is in compute-bound configs (C ≥ 256).
  • Fusion. At C=64 FlexGEMM is near bandwidth-bound, so gains have to come from moving fewer bytes. Fuse bias, norm, and activation into the epilogue, and read grad_output once for both the weight and input gradients.
  • Hybrid dispatch. Send dense leaves to the leaf-dense IGEMM, where pred_gather_igemm is a good fit, and sparse leaves to the masked IGEMM.

Scheduling with the VoxelBlockManager

#747 caches a NanoVDB VoxelBlockManager (VBM) per grid. The VBM splits active voxels into blocks of 128 and decodes each active index to its leaf and offset in O(1). The conv backend should use it to schedule work, but only if the neighbor probes also change. #747 found that moving GatherScatterDefault's build onto the VBM made it 10–25% slower, because that build's cost is the 27 tree probes per voxel, not the iteration.

Neighbor-map build

Launch one CTA per VBM block. On these shells a block spans about two leaves. firstLeafID and the jump map identify those leaves, and the CTA stages their 3×3×3 neighborhoods in shared memory. Taps then resolve with bitmask tests and popcounts, every thread does real work, and no thread walks the tree.

The same builder can emit the gather-scatter rulebook. That closes the probe-restructuring item in #817.

GEMM tiles

A VBM block is 128 leaf-ordered output rows, which is already the shape of an implicit-GEMM tile. If leaf order or a within-leaf sort wins the tile-ordering benchmark, VBM blocks become the tiles and sorted_idx goes away. If a global Gray sort wins, the VBM only helps the build.

Map-free mode (optional)

Each GEMM CTA decodes its rows through the VBM and resolves neighbors on the fly. This replaces ≈112N bytes of map with 0.16 B/voxel of VBM, but the probes rerun on every forward and backward pass of every layer. It suits large C, where the GEMM hides probe cost.

Prerequisites from #817

  • One launch per batch. ConvolutionPlan works on GridBatch, but VBM iteration launches once per grid. Batches of many small grids stay launch-bound until the per-block grid index lands.
  • No first-use host sync. Until openvdb#2291 merges, the VBM cold build does a blocking device read. Building a plan would then sync the host and couldn't run under CUDA-graph capture.
  • The GEMM keeps its own launch shape. #747 saw __launch_bounds__(512) silently drop work from a register-heavy callback. GEMM kernels should call decodeInverseMap directly instead of running through forEachActiveVoxelVbmCUDA, with a parity test that checks every output row is written.

FlexGEMM keeps a 27-wide neighbor map (108N), int64 sorted_idx (8N), gray_code (4N), and valid_signal_i/o pair lists (8P). Those pair lists duplicate fVDB's rulebook.

Trimming the port

  • Store sorted_idx as int32 (saves 4N).
  • Drop gray_code after sorting (saves 4N).
  • Compute the weight gradient from the map's tap column with masked tiling instead of pair lists (saves 8P). This wastes some work on rows without that tap, so benchmark it before committing.

The layouts break even at P/N = 13.5. Thin shells (12.7) cost about the same either way. Dense volumes approach 27, where the map costs half as much as the rulebook.

Working memory per training step

This term outweighs the topology. Gather-scatter sizes its scratch buffers to the largest tap segment, which for submanifold conv is the center tap with all N voxels. Forward needs N×(Cin+Cout) elements and backward needs N×(2Cin+Cout), plus K×Cin×Cout per weight copy. At 1024,64 in fp16 that comes to 1.0 GB forward and 1.6 GB backward. Implicit GEMM reads features in place, so this term goes away. That is why FlexGEMM's peak is lower in every config above, despite its larger cache (tf32 at RES=1024: 5.9 GB vs 8.4 GB).

Quick fixes to gather-scatter

These are worth doing even if the new backend lands, because gather-scatter stays the general fallback. Point 2 above sets their ceiling at about parity with FlexGEMM.

  • Fix the weight-layout mismatch between nn.SparseConv3d storage and gs_conv's permute.
  • Vectorize gather and scatter (half2/float4 loads, 32-bit indexing, per-row threads).
  • Run the submanifold center tap as a direct GEMM into the output, with no gather or scatter.
  • Fuse the gather into the GEMM's A-load and the scatter into its epilogue (CUTLASS gather/scatter GEMM).
  • Replace the 27 per-tap GEMMs with one grouped GEMM to cut launch overhead on small grids.
  • Build the rulebook in one pass using the leaf-cooperative probe.

Suggested next steps

  1. Write the staged-leaf probe builder on VBM scheduling. Benchmark it against FlexGEMM's 4 ms build at RES=1024 and against the current leaf scan.
  2. Have the same builder emit the gather-scatter rulebook, which closes the #817 probe item.
  3. Port FlexGEMM's forward, input-gradient, and weight-gradient kernels as a masked_igemm plan backend, plus the reverse map that strided and transposed plans need. FlexGEMM is MIT-licensed. Confirm attribution requirements before copying code.
  4. Benchmark the three tile orderings, which decide whether VBM blocks also serve as GEMM tiles. Then benchmark the trimmed weight-gradient path.
  5. Rewrite the hot path as a Blackwell-native CuTe kernel and fuse the epilogue.

Notes

  • The benchmark rebuilds topology every iteration, as FlexGEMM's original script does. Training on a fixed grid would remove most of fVDB's plan-build penalty from the comparison.
  • FlexGEMM's backward crashes when bias=None (submanifold_conv3d.py:358). The benchmark always passes a bias.
  • Triton 3.7.1 on SM120 needs TRITON_PTXAS_BLACKWELL_PATH set to the CUDA 13 ptxas.
  • Benchmark and profiling scripts are available on request.
